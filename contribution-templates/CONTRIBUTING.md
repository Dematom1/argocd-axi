# Contributing to {repo}

Thanks for wanting to help. This page is the whole contribution contract: agree on the change, raise it through no-mistakes, let the maintainer authorize full CI, work through review one head at a time, and leave the merge to the maintainer.

## 1. Agree on the change first

- **Bugs** are welcome without asking first. Open a [bug report](https://github.com/{owner}/{repo}/issues/new/choose) with the exact version, a reproduction, the expected and actual behavior, and sanitized output.
- **Substantial fixes and features** need an accepted scope before you write code. Search the open issues and pull requests, then open an issue that says what you want to change and how far the change goes. The maintainer checks it against current `main` and open work, classifies its contract effect (below), and adds the `ready-for-pr` label with a short note on scope and validation. Wait for that label. A green pipeline does not oblige the maintainer to accept scope that was not agreed.
- **Tiny documentation fixes**, such as a typo with no behavior change, can go straight to a pull request.
- **Security problems** never go in a public issue or pull request. If the repository's Security tab offers "Report a vulnerability", use it. Otherwise open an issue that says only that you have a security report and need a private contact, with no details.

Never put secrets, tokens, live credentials or unredacted production output in an issue, a pull request or a test fixture.

## 2. Classify the contract effect

Every issue and pull request states its effect on the existing project contract:

- **restore** - returns behavior or guarantees that regressed from the existing contract. May merge after review and green checks.
- **opt-in** - adds behavior without changing existing defaults or guarantees. May merge after review and green checks.
- **new-default** - changes the default behavior or existing contract. Waits for an explicit maintainer decision; do not merge until approved.
- **cannot-tell** - the evidence is not enough to classify the effect. Must not receive merge authority.

## 3. Raise the pull request through no-mistakes

Every human-authored pull request to `main`, including the maintainer's own, must be raised through [no-mistakes](https://github.com/kunchenguid/no-mistakes) v1.46.0 or newer. The required check `PR must be raised via no-mistakes` verifies that the PR body carries the no-mistakes signature and an attestation bound to the current head commit, with the review, test and document steps completed. Only the release App's release-please PR and Dependabot are exempt, and their check reports an exemption, not a validation.

1. Fork the repository, then clone the parent or set your local `origin` to it: `git@github.com:{owner}/{repo}.git`.
2. Create a branch and make your change.
3. Initialize the gate with your fork as the push target: `no-mistakes init --fork-url git@github.com:<you>/{repo}.git`. With push access to the parent, plain `no-mistakes init` works.
4. Commit, then push through the gate instead of to `origin`:

   ```sh
   git push no-mistakes
   ```

5. Run `no-mistakes` to attach to the pipeline and answer its findings. When every step passes it pushes to your fork and opens the pull request against `main`.

The pull request title must be a conventional commit (`feat:`, `fix:`, `docs:`, `chore:`, ...). In the PR body, keep the generated Pipeline, Intent and evidence sections intact when you edit it, and add the accepted issue (or the tiny-docs exception), the contract effect, the commands you ran with their results, and anything you could not test.

## 4. CI on outside pull requests

The cheap checks always run: PR title, `PR must be raised via no-mistakes`, and `Generated files must not be hand-edited`. They read PR metadata only and never run your code.

The full test suite on a pull request from a fork waits for the maintainer. After reviewing the change's source, dependencies, workflow edits and scope, the maintainer adds the `full-ci` label, and every later push runs the suite again. Until then the `Full suite` check fails with a message naming the label; that is expected and needs no action from you. Removing the label revokes the go-ahead. GitHub may also hold a first-time contributor's workflow runs for approval; that approval is separate from `full-ci`. Neither one is permission to merge, and CI never gives a pull request access to secrets. Branches in this repository run the full suite without the label.

`CHANGELOG.md` and `.release-please-manifest.json` are generated by release-please, so never edit them by hand.

## 5. Review

CodeRabbit reviews each pull request. Its findings are advisory: the maintainer decides which ones matter. Handle the whole completed review for the current head at once. Check every affected caller, rerun the tests you touched plus the meaningful regression, then make one repair push through no-mistakes. If you disagree with a finding, say why with evidence.

## 6. Merge

The maintainer approves each CI authorization, public comment, close and merge individually; there is no standing delegation. A pull request merges only with green required checks on its current head, resolved review conversations, an accepted scope and, for **new-default**, an explicit decision. When only CI authorization, review or the merge decision remains, the maintainer is the next actor; you do not need to rerun your pipeline to wait.

Releases are separate. release-please turns conventional commits on `main` into a release pull request, which a weekly workflow merges once it is green.
